Pinned bottom bar

A slim, blurred bar above the home indicator, similar to Photos/Files action bars. Reachable one-handed, always visible without competing with row content or the nav bar.

Discoverability high  ·  Disruption low (shrinks list by ~44pt)  ·  Familiarity common toolbar pattern

Copy options for the button label

  • Paste from Clipboard — clearest verb + object, matches system vocabulary (recommended).
  • Check Clipboard — accurate to what happens technically, but reads more like a status check than an action.
  • Add from Clipboard — emphasizes the outcome (a new saved item) over the mechanism.
  • Paste to Clippd — shortest, works well icon-only with a tooltip as backup.

Recommendation

A (pinned row) or D (bottom bar) are the strongest fits: both stay visible without a coach mark, and neither implies "create new" the way a FAB does. A keeps the mental model closest to today's pending-item row, so it's the smallest behavior change for existing users. D is a close second if the top of the list should stay purely search + filters.

Why this replaces the current flow

Today, ClipboardReader.readAndInsertPending runs on every foreground and .onAppear, which reads UIPasteboard.general without a direct user gesture — that's what triggers iOS's "Allow Paste" prompt. Moving the read behind a tap on one of these buttons means the tap itself is the user's consent. On iOS 16+, SwiftUI's native PasteButton is built exactly for this: it lets the system fulfill the paste without ever showing the permission banner, since the button owns the gesture. Worth using for whichever placement you pick, so the button both looks native and behaves natively.

Outcome

Option D (sticky bottom bar) was selected and implemented in clippd/Views/HomeView.swift, using SwiftUI's native PasteButton. It was later repositioned as a circular FAB next to a shrunk custom search field, in the same row — see the app for the current, real implementation; this file is a historical snapshot of the exploration that led there.
